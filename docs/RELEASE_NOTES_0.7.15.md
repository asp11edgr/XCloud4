# XCloud4 0.7.15 — receiving SSRC, track order and Teredo

The owner resumed development after the preserved 0.7.14 refusal and authorized all three audit-related changes together. Product version is **0.7.15**, with PS4 **APP_VER 00.85** and the existing application identifier **XCLD00001**. The PS4 interface remains Spanish. **A successful build or static review does not establish an accepted Xbox SDP answer, ICE connection or game video/audio.**

## Changes

1. The pinned libdatachannel C API omits an undefined local SSRC only for a receiving-only track with zero SSRC and no name, msid or trackId. This prevents the incomplete `a=ssrc:0` attribute generated by the previous two `rtcAddTrackEx` calls. Explicit metadata and other directions retain their original behavior. The patch is reproducible through `scripts/webrtc/prepare_port.py`.
2. Track creation now places audio at MID 0 before video at MID 1, following PSBox's order. Both XCloud4 tracks remain receiving-only; H.264 payload 102/profile `42e01f`, Opus payload 111 and the existing codec parameters remain. Reception is routed by track handles and media kind.
3. Remote candidate processing expands validated Teredo addresses into IPv4 UDP routes at the decoded port and fixed port 9002. Candidate MID is retained. Existing IPv4 handling and the signaling envelope remain. Arbitrary IPv6 addresses are not converted. The parser supports complete/compressed hexadecimal IPv6, rejects zones and dotted IPv4 tails, and rejects decoded IPv4 in 0/8, 127/8 and 224/3. Derived and original candidates share the existing 128-entry cache; enough distinct expansions can still hit its explicit bound.

SSRC grammar is a concrete local source defect identified by the supplied audit. Its supplied Chromium parser results have not been reproduced here and do not prove why Xbox rejected the old offer. Track order is an interoperability experiment. Teredo handling occurs after a usable remote SDP answer and therefore does not itself explain the previous refusal before that answer. Combining these changes limits causal attribution if behavior changes.

## Console status

The owner installed 0.7.15 and reported CE-34878-0 after connection failure. The captured log contains two distinct 0.7.15 launches. Both confirm a **1266-byte local offer**, `ssrc=0 bare_ssrc=0 first_kind=2 second_kind=1`, audio MID 0 and video MID 1. Xbox returns valid direct SDP answers: the first HTTP 200 response is **1865 bytes**, with **1503 decoded SDP bytes**; the second is **1867 bytes**, with **1505 decoded SDP bytes**. Both answers are applied and session state advances to negotiating ICE.

Local ICE submission returns HTTP 202. Remote ICE GET returns HTTP 200 (**449 / 451 bytes**, respectively); both log IPv6 classification 1 (omitted), with no Teredo expansion. That class alone cannot distinguish ordinary IPv6 from a Teredo candidate rejected by a validation rule. RTC then fails; session DELETE returns HTTP 200 without a cleanup error. Video/audio counters remain zero. Neither discarded-candidate classification nor RTC failure establishes the root cause.

After cleanup, each attempt logs **`terminating with uncaught exception of type std::__1::system_error: condition_variable timed_wait failed: Operation timed out`** and a fatal thread exception (**0xa002031a**, RIP **0x00000008000015bc**). This identifies an uncaught timed-wait exception as the immediate application-termination path; the native/runtime ABI cause is under investigation. Successful SDP application is progress beyond the old exchange refusal, but **no connected media transport or game playback is confirmed**. The combined changes do not identify which change enabled the valid answer.
